### The Solution: "Replay" (The Time Travel Trick)

The trick is that **the code *looks* like it pauses, but the system actually kills the process and restarts it later.**

When the user approves the action 2 days later, we run the script **from the top**. However, the **MCP Client** inside the sandbox is smart: it checks the Flight Recorder. If a step has *already happened*, it doesn't run it again—it just returns the saved result instantly.

This allows your Python code to use standard `await`, but your infrastructure (IX Service) to save resources.

  * **Action:** It performs a **SELECT** on the `ingest_jobs` table.

### 3\. The New Workflow Code (How LLMs Use It)

```python
import mcp
import asyncio

async def main():
    # 1. THE HANDOFF
    # The Sandbox calls the MCP Server.
    # The MCP Server inserts the row into Postgres Queue.
    print("Submitting ingestion job...")
    response = await mcp.use("kb_core", "ingest_submit", 
                             url="https://docs.python.org/3/")
    
    job_id = response["job_id"]
    print(f"Job started: {job_id}")

    # 2. THE WAIT LOOP (Native Python Logic)
    # The Ingestion Worker (Pillar 1) is now churning in the background.
    # The Sandbox just polls lightly to check progress.
    while True:
        status = await mcp.use("kb_core", "ingest_status", job_id=job_id)
        
        if status["state"] == "completed":
            print("Ingestion finished!")
            break
        
        if status["state"] == "failed":
            print(f"Job failed: {status['error']}")
            # We can even add "Self-Healing" logic here!
            return

        print("Working...")
        await asyncio.sleep(5) # Wait 5 seconds before checking again

    # 3. THE NEXT STEP
    # Now that the queue is empty, we can search the new data.
    results = await mcp.use("kb_core", "search", query="asyncio loops")
```

### Why You Can't "Just Let MCP Handle It"

If you removed the Queue and made the Ingestion Worker part of the MCP Server directly:

1.  **Timeouts:** Most HTTP/MCP clients have a 60-second timeout. If ingestion takes 61 seconds, the connection dies, the error is thrown, but the server is still burning CPU. It's a mess.
2.  **Concurrency:** If 10 users submit jobs, you spawn 10 heavy processes instantly, crashing your server. The Queue (`SKIP LOCKED`) ensures you only run 2 or 4 jobs at a time, regardless of how many requests come in.
3.  **Resilience:** If the server crashes mid-job, a direct MCP call is lost forever. With a Queue, the job stays in Postgres. When the server restarts, the Worker picks it up again.

### Final Decision

**Keep the Queue.** It is the engine room of Pillar 1.

  * **MCP Client Manager** is the **Router** (It connects wires).
  * **MCP Server (kb-core)** is the **Receptionist** (It takes the job ID).
  * **Postgres + Worker** is the **Factory** (It does the work).

Your architecture is now fully compliant with **Code Mode** while retaining **Enterprise Durability**.
