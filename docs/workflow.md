Here is the proper explanation of your 4-layer hierarchy (Tools → Skills → Workflows → Missions) and why merging them would be a mistake.

### The Hierarchy of "Governed Code Mode"

We are moving from a "Configuration" mindset (YAML) to a "Software" mindset (Python). Here is how your layers stack up now:

#### 1. Underlying Tools (The Atoms)
* **What they are:** Raw, atomic MCP capabilities.
* **Examples:** `filesystem.read_file`, `postgres.query`, `http.get`.
* **Where they live:** **Pillar 0 (Action Gateway)**.
* **Role:** These are the **System Calls**. They are "dumb" I/O operations. They have no business logic. They are the only things that actually touch the outside world.

#### 2. Skills (The Molecules)
* **What they are:** Sandboxed, pre-written Python/TypeScript libraries that `import` Tools.
* **Examples:** `xlsx.clean_data` (uses `fs.read`), `git.clone_and_analyze` (uses `http` + `fs`).
* **Where they live:** **Pillar 1 (Knowledge Foundation)** stores the code; **Pillar 0** executes them.
* **Role:** These are **Standard Libraries**. They encapsulate complex logic (like parsing a spreadsheet) so the LLM doesn't have to hallucinate it. They are human-verified and safe.

#### 3. Workflows (The Blueprint / The Code)
* **What they are:** The **Python Script** (`.py` file) generated by the Planner.
* **Examples:** `monthly_report.py`, `onboarding_flow.py`.
* **Where they live:** **Pillar 1 (Knowledge Foundation)** stores them as versioned artifacts.
* **Role:** This is the **Business Logic**. It imports **Skills** and **Tools** to solve a specific user goal.
    * *Crucially:* Since we dropped YAML, this file now contains all the `if/else`, `while`, and `try/catch` logic natively. You don't need a custom interpreter anymore.

#### 4. Missions (The Runtime Process)
* **What they are:** The **Container** that executes a Workflow.
* **Examples:** "Mission #994: Run `monthly_report.py` for Tenant A, triggered by Scheduler at 9 AM."
* **Where they live:** **Pillar 2 (IX Service / Control Plane)**.
* **Role:** This is the **Process ID (PID)**.
    * It holds the **State** (Running, Paused, Failed).
    * It holds the **Context** (Variables, Secrets, User ID).
    * It owns the **Flight Recorder** trace (Audit logs).
    * It manages **Triggers** (Webhooks, Schedules).

---

### Why You Must Keep Them Separate

If you merge "Workflow" and "Mission," you essentially say "A script can only run once."

By keeping them separate, you gain **Scale and Governance**:

1.  **Reusability:** One Workflow (`data_pipeline.py`) can be run by 1,000 different Missions (one for each customer, or one every hour).
2.  **Auditability:** The **Workflow** is the *Static Definition* (what we *planned* to do). The **Mission** is the *Dynamic Record* (what actually *happened*). Comparing them is how **Pillar 4 (Self-Healing)** works.
3.  **Resilience:** If a Mission crashes (e.g., API timeout), the Workflow code is fine. You just spawn a *new* Mission to retry it.
4.  **State Management:** The Workflow (Python code) is stateless. The Mission holds the state. This is critical for **"Human-in-the-Loop"**.
    * *Scenario:* The Python code hits `await human.approve()`.
    * The **Mission** pauses. It serializes the state to Postgres (Pillar 2).
    * The Python interpreter (Pillar 0) shuts down to save resources.
    * Days later, the user clicks "Approve."
    * The **Mission** wakes up, respawns the Python process, and resumes execution.

### The "No-YAML" Upgrade

You asked: *"As we are removing YAML, do we need logic here?"*

This is the best part. By removing YAML, **Pillar 2 (IX Service)** becomes much simpler.

* **Old Way (YAML):** The IX Service had to be a complex engine. It had to parse YAML, manage a stack, evaluate `if` statements, handle loops, and dispatch tools. It was basically a slow, buggy programming language interpreter.
* **New Way (Code Mode):** The IX Service is just a **Manager**.
    1.  It spawns a Sandbox (Pillar 0).
    2.  It injects the Workflow Code (`.py`).
    3.  It says "Run."
    4.  It waits for the Sandbox to call back (for a Tool execution or a Human pause).

All the branching logic (`if x > 5`) happens inside the **Sandbox (V8/Python)** at native speed.

We will **kill** the concept of "Tier 1 System Bindings" as a separate mechanism.

Instead, the OS itself simply hosts internal MCP Servers.

#### 1\. The "Memory" MCP Server (Wraps Pillar 1)

You are right: The LLM inside the sandbox must **not** have direct access to the database.
Instead of a magic `import memory`, we treat the Knowledge Foundation (Pillar 1) as just another MCP Server.

  * **How it works:** We build a lightweight MCP Server (e.g., `kb-core-mcp`) that exposes `search` and `graph_walk`.
  * **Security:** When the sandbox calls `await use_mcp_tool("kb_core", "search", query="...")`:
    1.  The call is trapped by the **Policy Gate (Pillar 0)**.
    2.  The Gate sees: "Agent requesting `kb_core.search`".
    3.  The Gate checks the **ABAC Filter** (passed from Gateway).
    4.  **CRITICAL:** The Gate *injects* the user's ABAC filter into the arguments before forwarding the call to Pillar 1.
  * **Result:** The LLM *cannot* search without policy, because the tool interface *requires* the Policy Gate to inject the filter.

#### 2\. The "AI" MCP Server (Wraps Pillar 2 / ICE)

You are right: We cannot let the LLM wildly call `ai.synthesize` and burn tokens or create recursive loops without oversight.
We treat the AI capabilities as an MCP Server (e.g., `ice-mcp`).

  * **Capabilities:** `generate_text`, `summarize`, `reason`.
  * **Governance:** Because it is an MCP tool, we can put **Rate Limits** and **Budget Caps** on it in the Policy Gate. If an agent tries to call `ai.generate` 100 times in a loop, the Policy Gate cuts it off.

#### 3\. The "Human" MCP Server (Wraps Pillar 3 UI)

  * **Result:** The code inside the sandbox just awaits a function. It doesn't know it's paused.

### The Final, Unified Architecture

This addresses your concern about "forcing a separate language." We use **Native Python**, but we govern *every single import* as an MCP interface.

**The Code (Written by LLM / Planner):**

```python
# No magical "System Imports". Just standard MCP calls (or a clean wrapper lib).
# This code runs in the Sandbox (Pillar 0).

import mcp  # Our single, governed client library

async def main():
    # 1. MEMORY: Secure, Policy-Gated Call
    # The Policy Gate intercepts this and injects the ABAC filter.
    docs = await mcp.use("kb_core", "search", query="Project Alpha")

    # 2. LOGIC: Native Python (No DSL needed!)
    # We use Python's native 'if', 'for', 'while'.
    urgent_docs = [d for d in docs if "urgent" in d['tags']]

    if not urgent_docs:
        print("No urgent docs found.")
        return

    # 3. AI: Governed Intelligence
    # The Policy Gate checks the token budget before allowing this.
    summary = await mcp.use("ice", "summarize", text=urgent_docs)

    # 4. HUMAN: The UI Hook
    # This triggers the "Mission Pause" in Pillar 2.
    approved = await mcp.use("human", "ask", question=f"Send this summary? {summary}")

    if approved:
        # 5. EXTERNAL TOOL: Standard MCP
        await mcp.use("slack", "send", channel="#updates", text=summary)
```

### Why This is Better (Your "Learning"):

1.  **Uniform Security:** There is only **one** security boundary: The **Policy Gate**. It handles Memory, AI, Slack, and Filesystem exactly the same way. There are no "special system backdoors."
2.  **Native Logic:** As you said, "we do not need DSL." We use Python for branching (`if`), looping (`for`), and data manipulation. We only intercept the **I/O** (the `mcp.use` calls).
3.  **Policy Isolation:** The Code (Sandbox) never holds the ABAC Filter or the User ID. The **Policy Gate** holds those. The Code just asks "Search for X", and the Gate attaches "For User Y with Permissions Z".

**Decision:** We drop "System Primitives." We have **only** MCP Servers (Internal & External) and **Native Python** logic.
